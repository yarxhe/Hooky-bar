# Проверка панели: реальные кнопки, CPU и память

Этот тест управляет **обычной уже запущенной Hooky bar**, а не макетом SwiftUI или отдельным тестовым окном. Native Accessibility нажимает настоящие кнопки. Раскрытие/сворачивание вызывается движением указателя; прокрутка — событием в области списка панели. Анимации, частота кадров, эффекты оформления, музыка и пользовательские настройки тестом не отключаются.

## Запуск

Установить актуальную локальную сборку и запустить её. Она содержит невидимые accessibility-идентификаторы главной панели, вкладок и фильтров. Не запускать другую сборку одновременно.

Из корня репозитория:

```sh
Packaging/test-panel-performance.sh --report /tmp/hooky-panel-before.json
```

При необходимости явно выбрать установленное приложение:

```sh
Packaging/test-panel-performance.sh --app "/Applications/Hooky bar.app" --report /tmp/hooky-panel-before.json
```

Нужен доступ «Универсальный доступ» для запускающего терминала. Если его нет, тест остановится без автоматического запроса разрешения. На этой машине используются Command Line Tools без изменения глобально выбранного Xcode:

```sh
DEVELOPER_DIR=/Library/Developer/CommandLineTools Packaging/test-panel-performance.sh --report /tmp/hooky-panel-before.json
```

Прогон занимает примерно 3 минуты. Не трогать мышь и интерфейс. Движение мыши или удержание Escape останавливает тест; при ручном вмешательстве указатель не возвращается принудительно. Файл отчёта должен быть новым: существующие отчёты не перезаписываются.

## Сценарий

Два прогревочных цикла не входят в итоговые метрики. После них — 10 секунд закрытой панели и 8 измеряемых циклов:

1. Наведение раскрывает панель; проверяется появление её кнопок.
2. Нажатия «Утилиты», «Буфер»; проверяется выбранное состояние.
3. По очереди фильтры «Текст», «Скрины», «Важное», «Все»; проверяется каждый.
4. Если Dev уже включён — его кнопка, прокрутка вниз/обратно с проверкой изменения нативного scrollbar. Если контент помещается без прокрутки — это явно отмеченный пропуск, не успех прокрутки.
5. Возврат на «Музыку», уход курсора, проверка исчезновения кнопок.
6. 3 секунды ожидания, затем 1,5 секунды замера в одинаковом свёрнутом состоянии.

В конце — ещё 10 секунд восстановления. `--cycles 3` подходит для короткой отладки, `--cycles 30` — для более длинного прогона. Для сравнения число циклов должно совпадать.

Тест не нажимает воспроизведение, очистку, удаление, добавление/редактирование заметок, копирование или запуск внешних приложений. Dev не включается автоматически. Остаются только обычные побочные эффекты навигации, например штатное обновление Dev. Закрытая/открытая панель и последняя вкладка могут отличаться от состояния до теста.

## Что измеряется

Из `proc_pid_rusage` конкретного процесса каждые 250 мс, отдельно от ресурсов самого теста:

- CPU: разность накопленного пользовательского и системного времени / реальный интервал. Mach-тики переводятся через `mach_timebase_info`, а не считаются наносекундами. 100% — одно ядро; значения выше 100% не обрезаются.
- CPU каждой фазы: взвешенное по времени среднее, p95 и максимум **интервальных** измерений, не мгновенный аппаратный пик.
- Physical footprint, MiB (1 048 576 байт), не RSS; медиана и максимум каждой фазы.
- Разница памяти после восстановления относительно прогретого состояния до циклов.
- Память после каждого сворачивания и её линейный тренд MiB/цикл. Положительный тренд — повод исследовать удержание объектов, а не доказательство утечки сам по себе.

Дополнительные замеры на границах фаз сохраняют CPU первого кадра, но иногда дают очень короткие интервалы. Их максимумы чувствительны к точности счётчиков: при разборе пика нужно смотреть `duration` в сырых данных. Среднее взвешено по времени; p95 — по количеству интервалов, не доле времени. Не использовать единичный субмиллисекундный пик как оценку постоянной нагрузки.

JSON содержит сырые измерения, конфигурацию, окружение, число проверенных действий и причину остановки. Текст заметок, содержимое буфера, названия треков/проектов не сохраняются. При перезапуске процесса, отсутствии кнопки или неподтверждённом действии результат будет `completed: false` и код выхода 2.

Актуальная схема отчёта — **2**. Экспериментальные отчёты схемы 1 занижали CPU на Apple Silicon из-за неверных единиц времени; их CPU-значения недействительны и сравнение с новой схемой запрещено. Память измерялась независимо от этого пересчёта. Для нового baseline нужно выполнить новый прогон.

## Проверка регрессий

Первый запуск выдаёт **MEASURED**, а не «производительность хорошая». Сначала нужно оценить и сохранить подходящий базовый прогон. После изменения приложения:

```sh
Packaging/test-panel-performance.sh --report /tmp/hooky-panel-after.json --baseline /tmp/hooky-panel-before.json
```

Сравниваются только завершённые прогоны с одинаковыми сценарием, действиями/пропусками, ОС, числом CPU, дисплеями, Reduce Motion, режимом энергосбережения и набором запущенных поддерживаемых музыкальных приложений (`musicApps`: Apple Music, Spotify, Яндекс Музыка). Старый отчёт без `musicApps` не принимается как baseline. Набор проверяется перед каждым циклом и после восстановления; обнаруженное изменение прерывает прогон. Это не непрерывный мониторинг: краткое закрытие/открытие между проверками может остаться незамеченным. Допуски от базового результата:

- Средний CPU: +25% и 3 процентных пункта; p95: +35% и 8 пунктов.
- Пиковый footprint: +20% и 8 MiB.
- Удержанная память: дополнительно 12 MiB; тренд: дополнительно 1,5 MiB/цикл.

Это стартовые допуски регрессионного теста, **не гарантия комфортной производительности**. Высокая нагрузка уже в baseline не станет ошибкой сравнения сама по себе. Поле `musicApps` проверяет присутствие плееров, а не состояние воспроизведения. Воспроизведение музыки, объём содержимого, другие приложения и температура устройства тоже влияют на результат; их нужно сохранять сопоставимыми вручную. CPU WindowServer/GPU и дочерних процессов не входит в CPU Hooky bar.

Коды выхода: 0 — сценарий измерен (либо сравнение прошло), 1 — регрессия/несопоставимый baseline, 2 — ошибка или незавершённый прогон. При первом запуске отсутствие baseline явно написано в выводе.

## Автотесты измерителя

`Packaging/test.sh` также запускает `HookyPerformanceTests`: расчёт CPU >100%, перевод тиков на Apple Silicon и Intel, сверка настоящего `proc_pid_rusage` с независимым `getrusage` под короткой нагрузкой, взвешенное среднее, отсутствие ложного нуля для пустых данных, исключение прогрева, отличие пиков от удержанной памяти, обнаружение регрессий, JSON round-trip и отказ сравнивать разные/незавершённые прогоны. Эти unit-тесты проверяют измеритель, **не заменяют живой UI-прогон**.

Исполняемый проверяющий инструмент собирается отдельно. В установленный `.app` он не попадает и фонового мониторинга не добавляет. Сравнение разных или не зафиксированных музыкальных нагрузок также покрыто unit-тестом.
