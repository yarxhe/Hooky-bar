# Архитектура Hooky bar

[Русский](Architecture.md) · [English](Architecture.en.md)

Этот документ описывает фактическую архитектуру текущего приложения. Запланированные публичные API вынесены в [план SDK](SDK-Plan.md).

## Слои

```text
┌─────────────────────────────────────────────────────┐
│ SwiftUI Views                                       │
│ MusicPane · ClipboardPane · ToolsPane · Developer   │
└───────────────────────┬─────────────────────────────┘
                        │ намерения пользователя
┌───────────────────────▼─────────────────────────────┐

│ Adapters                                            │
│ Music · Clipboard · Notes · Tools · System adapters │
└───────────────────────┬─────────────────────────────┘
                        │ системные API / IPC
┌───────────────────────▼─────────────────────────────┐
│ macOS · Яндекс Музыка · Apple Music · Spotify · gh  │
└─────────────────────────────────────────────────────┘
```

### Представления

SwiftUI-представления читают опубликованное состояние и вызывают методы сторов. Они не должны:

- выполнять AppleScript;
- читать `NSPasteboard`;
- запускать процессы;
- обращаться к CDP, Accessibility, EventKit или IOBluetooth;
- определять fallback между несколькими внешними API.

### Сторы

Стор — единственный владелец состояния конкретной функции. Он:

- выбирает подходящий адаптер;
- управляет жизненным циклом наблюдения;
- объединяет данные нескольких источников;
- обновляет состояние только на главной очереди;
- выполняет optimistic update и последующую сверку, если команда внешнему приложению не мгновенная;
- не содержит деталей конкретного внешнего приложения, если их можно оставить в адаптере.

### Адаптеры

Адаптер скрывает конкретный способ интеграции: AppleScript, MediaRemote, CDP, Accessibility, файловый watcher, `gh` или системный URL. Внешний сервис может измениться без переделки UI и основного стора.

## Композиция приложения

Корневые зависимости создаются в `AppDelegate`:

- `MusicStore`;
- `ClipboardStore`;
- `NotesStore`;
- `ToolsStore`;
- `VolumeStore`;
- `SystemFeatureStore`;
- `IntegrationDiagnosticsStore`;
- `InterfaceModel`;
- `AppLocalization`.

Они живут столько же, сколько процесс приложения. Мониторинг запускается в `applicationDidFinishLaunching` и останавливается в `applicationWillTerminate`.

## Локализация

`AppLocalization` хранит выбор `system`, `russian` или `english`. Режим `system` следует за языком macOS: русская системная локаль выбирает русский, остальные — английский. Пользовательские строки проходят через `L10n`, поэтому SwiftUI, AppKit-меню, системные события и адаптеры используют один язык и переключаются без перезапуска.

Строки, которыми музыкальный адаптер ищет элементы интерфейса внешнего приложения, не являются переводами Hooky bar. Они остаются внутри конкретного адаптера и не должны зависеть от выбранного языка приложения.

## Потоки данных

### Команда пользователя

```text
Button
  → Store method
  → capability check
  → selected adapter
  → external command
  → refresh / acknowledgement
  → @Published state
  → View update
```

Музыкальные команды дополнительно используют временное ожидаемое состояние. Это не даёт устаревшему ответу плеера несколько раз менять play/pause до подтверждения команды.

### Событие источника

```text
External source
  → Adapter callback
  → Store normalization / merge
  → @Published state on main queue
  → View update
```

Так работает буфер: каждый источник публикует полный снимок своих элементов и, при наличии, отдельно новый элемент.

`ClipboardRetentionPolicy` ограничивает общую историю 48 незакреплёнными элементами и сроком 24 часа. Закреплённые элементы не участвуют в лимите. Автоматическая и ручная очистка передают элементы соответствующим адаптерам одной пакетной операцией; системный clipboard и исходные файлы скриншотов не удаляются.

## Состояние и идентичность

- Идентификатор адаптера должен быть стабильным между запусками.
- Идентификатор элемента должен быть уникальным внутри источника.
- Снимки состояния должны быть значениями, а не ссылками на UI.
- Адаптер не должен сам изменять состояние SwiftUI.
- Store обязан отбрасывать поздний ответ, если пользователь уже переключил источник.

Для музыкального трека идентичность сейчас вычисляется из нормализованных названия и исполнителя. При её изменении сбрасываются прошедшее время, временное состояние рейтинга и кэш следующего трека.

## Потоки и производительность

- UI и `@Published` обновляются на `DispatchQueue.main`.
- AppleScript, CDP, Git и `gh` выполняются вне главной очереди.
- Polling должен иметь ограниченную частоту и прекращаться вместе со стором.
- Наблюдатели обязаны быть идемпотентными: повторный `start` не создаёт второй watcher или timer.
- Callback адаптера не должен удерживать store сильной ссылкой.
- Каждый асинхронный callback привязан к поколению lifecycle: ответ от прошлого источника или остановленной сессии отбрасывается и не снимает блокировку с нового запроса.
- Файловый `DispatchSource` закрывает захваченный при создании descriptor, а не общее изменяемое поле: поздний cancel-handler не может закрыть watcher новой сессии.
- Событийные системные API предпочтительнее фонового polling.

## Диагностика интеграций

`IntegrationDiagnosticsStore` формирует единый снимок состояния музыки, заметок, системных функций и developer-инструментов через `IntegrationDiagnosticsAdapter`. Потенциально медленные проверки CDP, GitHub CLI и системных доступов выполняются вне главной очереди; поздний результат устаревшей проверки отбрасывается.

Диагностика только читает уже доступное состояние и сама не вызывает системные запросы разрешений. Переход в настройки macOS выполняется только по явному нажатию пользователя. Для Automation macOS не предоставляет надёжную неинвазивную проверку до первого обращения, поэтому этот доступ обозначается как «проверяется при использовании».

Отчёт диагностики формируется отдельным pure builder и копируется через адаптер только по кнопке пользователя. В отчёт входят версия приложения, версия macOS и состояния интеграций; пути, содержимое буфера и медиаданные не включаются.

Операционные логи `controls`, `yandex-bridge` и `memory` также не содержат названий треков. Они выключены по умолчанию и управляются ключом `debugLogging` в `~/Library/Application Support/Hooky bar/config.json`. Конфигурация перечитывается во время работы приложения; перезапуск для переключения не нужен.

Периодический `memory` heartbeat включает physical footprint и средний CPU процесса за интервал (`cpu_percent`, `cpu_interval_s`), без обхода потоков и без отдельных частых таймеров. CPU считается по разнице пользовательского и системного времени процесса; 100% соответствует одному ядру. Первый замер задаёт базу.

HookyStick удалён 15 сентября 2026: приложение больше не создаёт его хранилище, окна и подписки; список, настройки и счётчик в heartbeat также удалены. Старые данные `stickyNotes.*` не очищаются и не читаются. Обычные интеграции заметок через `NotesStore` остаются.

Dev обновляет Git/GitHub при появлении, а не по постоянному таймеру. Повторные появления используют 15-секундный кэш и не дублируют ещё выполняющуюся проверку того же проекта. Ручное обновление обходит кэш (но не дублирует активный запрос). Выбор другого проекта запускает отдельное обновление; устаревший результат не заменяет новый. Ограничитель горизонтальной прокрутки учитывает допустимое нативное смещение `NSClipView`, не перенастраивает scroll view каждый кадр и защищён от рекурсивных уведомлений.

## Геометрия панели

`InterfaceModel` управляет переходами, а `HookySurfaceLayout` является единым источником геометрии для SwiftUI и AppKit hit testing. Новая интеграция не должна самостоятельно менять размер `NSPanel`; она передаёт событие или состояние хосту, а хост выбирает существующий режим поверхности.

Действующие режимы:

- `idle`;
- `compact`;
- `systemEvent`;
- `screenshotSuccess`;
- `expanded`;
- `screenshotPreview`.

Это ограничение особенно важно для SDK: расширения не должны создавать несовместимую геометрию острова.

### Нативная анимация внешней оболочки

`NativeSurface` сохраняет AppKit-host содержимого размером 440 × 314. Раскрытие, сворачивание, асимметричные крылья и режимы скриншота меняют маску `CAShapeLayer`, а не покадровый размер всего SwiftUI-дерева. Контур имеет одинаковую топологию во всех режимах, пружина Core Animation при быстром развороте начинается с текущего presentation path. У хоста нет собственного таймера и снимков содержимого. При Reduce Motion пространственная анимация отключается, короткие растворения сохраняются.

Геометрия берётся из `HookySurfaceLayout`; hover и hit testing исключают прозрачные поля. Входящие AppKit-координаты клика переводятся из superview в локальные координаты. Уход указателя закрывает панель и после открытия глобальным hover. Глобальный monitor нужен только свёрнутой панели, его события объединяются до 30 hit-test в секунду; открытая панель использует собственный `NSTrackingArea`. `refreshPanelRendering` только помечает layout/display как требуемые, без синхронной повторной отрисовки. Тесты проверяют постоянный размер, быстрые переходы, Reduce Motion, координаты и освобождение реального representable. Измерения и ограничения — в [отчёте 15 сентября](Native-Surface-Performance-2026-09-15.md).

### Нативный переход вкладок

`NativePaneTransition` размещает содержимое вкладок в AppKit `NSHostingView`. Сдвиг и прозрачность этих слоёв анимируются через Core Animation (`CASpringAnimation` / `CABasicAnimation`), отдельно от SwiftUI-layout содержимого. Геометрия внешней панели, анимации кнопок и цветной фон сохранены. Это точечная замена перехода, не переписывание всего интерфейса на AppKit и не гарантия низкой нагрузки сама по себе.

К окну прикреплены максимум две страницы: текущая и уходящая. Уходящая сразу исключается из hit testing и Accessibility, затем отсоединяется. `NativePaneCache` повторно использует только посещённые страницы (максимум четыре хоста суммарно), не сохраняя снимки экрана. Через 8 секунд после сворачивания панели или при предупреждении о памяти отсоединённые страницы освобождаются. Принудительного рекурсивного layout внутри `updateNSView` нет; содержимое большой панели получает конечный размер до анимации внешней оболочки. В независимый SwiftUI-root передаётся environment, включая локализацию. Reduce Motion оставляет короткое растворение. Жизненный цикл, быстрые переключения, состояние повторно используемых страниц, очистка кэша и сворачивание реального representable покрыты тестами.

Музыкальный фон сохраняет плавное изменение палитры и движение. `NativeLightRibbons` подготавливает градиентные слои при изменении размера/цвета; Core Animation перемещает растеризованные слои без `TimelineView`/`Canvas` на каждом кадре. При отсоединении, скрытии и Reduce Motion движение останавливается. Retina scale учитывается отдельно. Это уменьшает работу приложения, но не исключает нагрузку системного композитора.

### Тёмный материал вместо Liquid Glass

С 13 сентября кнопки и карточки используют `HookyMaterialBackground`: системный `.ultraThinMaterial` в тёмной схеме с нейтральным затемнением. Стеклянные блики, преломление, контуры, `GlassEffectContainer` и принудительная смена identity через ревизию стекла удалены. При Reduce Transparency используется непрозрачная тёмная заливка. Материал не перехватывает клики и не меняет размеры контрола; анимации переключения и раскрытия сохранены. Это изменение оформления, а не обещание устранить все причины нагрузки.

### Адаптивный mini-player

Когда есть компактный контент, `MenuBarCollisionDetector` читает через Accessibility границы menu bar активного приложения по обе стороны выреза. `AppDelegate` пересчитывает безопасную ширину левого крыла с обложкой и правого крыла с визуализатором раз в 1.2 секунды, а также непосредственно перед переходом из большой панели в compact. Вырез остаётся закреплённым по центру, а каждое крыло пружинно сжимается и растворяется отдельно. Если Accessibility недоступен, оба крыла сохраняют штатную ширину: это улучшение, а не условие работы плеера.

## Локальный канал Яндекс Музыки

Hooky является клиентом DevTools внутри Яндекса, а не отдельным веб-сервером. `CDPLocalRequest` использует `NWConnection` и системный `NWProtocolWebSocket`: короткое соединение на запрос, закрытие на успехе, ошибке и тайм-ауте, слабые обработчики событий. Максимум две операции одновременно (команда и фоновый опрос), один кэшированный URL страницы; нет истории ответов, cookie/cache или пула `URLSession`. Чтение системных медиаданных не менялось.

Проверка владельца порта сохраняется: только процесс внутри ожидаемого приложения, `127.0.0.1`, правильный порт и путь `/devtools/page/`. Отрицательная проверка/неудачное обнаружение повторяются не чаще раза в 3 секунды; явная команда пользователя обходит отрицательный кэш. Ответ WebSocket ограничен 512 КиБ и 32 сообщениями до нужного id. HTTP discovery ограничен 16 КиБ заголовков и 1 МиБ тела ещё при чтении; редиректы, сжатие и transfer encoding не поддерживаются и отклоняются. Поздний ответ после тайм-аута не удерживается. Испытания используют отдельный синтетический loopback-сервер, не музыку пользователя. Результаты — в [отчёте CPU/CDP](CPU-CDP-Fixes-2026-09-14.md).

## Beta-gate

Архитектурный beta-gate закрыт:

1. Команды адаптеров возвращают типизированные результаты и ошибки.
2. `MusicAdapterRegistry` расширяем и подключает все встроенные плееры через общий контракт.
3. `NotesAdapterRegistry` расширяем и подключает встроенные приложения заметок через общий контракт.
4. Bluetooth, VPN, Calendar и AirDrop реализуют общий `SystemEventAdapter`.
5. Разрешения интеграций описаны машинно-читаемыми `IntegrationCapabilityDeclaration`.
6. Для стабилизированных контрактов добавлены test doubles и регрессионные тесты.

Проверка контрактов запускается командой `./Packaging/test.sh`. После release-сборки, smoke-теста и измерения ресурсов версию можно публиковать как бету. Публичный SDK для этого не требуется. Требования перехода от публичной беты к стабильному выпуску намеренно отделены от архитектурного gate и описаны в [Beta readiness](Beta-Readiness.md).

## Архитектурные долги перед SDK

Эти задачи начинаются после выхода и стабилизации беты:

1. Вынести value-модели и протоколы из executable target в публичные Swift-модули.
2. Зафиксировать совместимость версий host и расширений.
3. Добавить изоляцию, проверку и безопасный жизненный цикл стороннего кода.

Только после этого можно объявлять публичный API стабильным.
