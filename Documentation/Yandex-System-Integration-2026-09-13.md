# Яндекс Музыка: системный канал и локальный CDP

Проверка 13 сентября 2026, macOS 27.0 (26A428), Яндекс Музыка 5.119.0. Это аудит текущего канала, не миграция музыкального адаптера.

## Что проверено на запущенном приложении

У процесса Яндекс Музыки не обнаружен слушающий TCP-порт; сохранённый CDP-порт Hooky `56574` также не слушается. Плеер не перезапускался, remote debugging не включался, воспроизведение и пользовательские данные не менялись.

Одноразовый запрос через уже используемый `MediaRemoteAdapter` вернул системный источник `ru.yandex.desktop.music`, название, исполнителя, обложку, длительность, позицию и состояние паузы. В отчёт проверки записывалось только наличие полей, не их содержимое. Полей рейтинга и следующего трека в этом ответе не было. Таким образом, **для базовых данных текущего системного плеера CDP-сервер не нужен**. Ответ на паузе не доказывает работоспособность всех команд или получение данных неактивного плеера.

## Как устроен текущий код

- `MusicAdapterRegistry` подписывается на MediaRemote. `MusicStore.applyTrackInfo` уже получает основные сведения системным путём.
- `YandexMusicAdapter.directSnapshot` предпочитает системные сведения, когда Яндекс владеет системным Now Playing; CDP — резерв.
- Адресные команды, чтение play/pause, рейтинга и очереди сейчас предпочитают CDP, затем Accessibility; системные команды применяются только при подтверждённом владении Now Playing. Это защищает от управления другим плеером.
- Hooky не поднимает отдельный HTTP-сервер. При запуске закрытого Яндекса через адаптер ему передаются параметры Electron для отладочного endpoint на loopback. Hooky подключается к его HTTP/WebSocket endpoint как клиент.
- Даже при наличии системных сведений остаётся опрос состояния воспроизведения каждую секунду и отдельные опросы рейтинга/очереди. Отсутствие CDP не кэшируется: каждая такая попытка может заново запускать `lsof`. Это конкретный кандидат на лишнюю фоновую работу, а не доказанная причина всего расхода CPU или роста памяти.

## Ограничения «системного» решения

Используемый пакет обращается к **приватному** `MediaRemote.framework` через вспомогательный процесс. Это не веб-сервер, но и не гарантированный публичный API Apple. Его совместимость нужно проверять на обновлениях macOS; встраивать обещания стабильного публичного SDK на этой основе нельзя.

Публичные [MPNowPlayingInfoCenter](https://developer.apple.com/documentation/mediaplayer/mpnowplayinginfocenter) и [MPRemoteCommandCenter](https://developer.apple.com/documentation/mediaplayer/mpremotecommandcenter) предназначены для публикации сведений собственного плеера и приёма команд им. Они не являются универсальной публичной заменой для чтения и адресного управления чужой Яндекс Музыкой. Сам используемый [MediaRemoteAdapter](https://github.com/ejbills/mediaremote-adapter) описывает зависимость от private framework. Механизм отладочного порта описан в [документации Electron](https://www.electronjs.org/docs/latest/api/command-line-switches#--remote-debugging-portport).

Рекомендованное направление: системная подписка как основной источник базового состояния; CDP/Accessibility — ограниченный резерв для отсутствующих возможностей; backoff отрицательных проверок с немедленным сбросом при запуске Яндекса или явной команде пользователя. Удалять весь резерв без тестов play/pause, cold launch, seek, лайков и смены активного плеера пока нельзя. В рамках этого запроса музыкальная маршрутизация не изменялась.
